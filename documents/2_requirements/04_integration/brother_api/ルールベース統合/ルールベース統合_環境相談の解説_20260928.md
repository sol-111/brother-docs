# ルールベース統合の環境相談（2026/09/28 柳さんメール）の解説

## 1. ひとことで言うと

ブラザーさんは、**画像の作り方を新方式（ルールベース方式）に入れ替える／追加する準備**をしています。
そのテストを、**いまユーザーが使っている本番アプリを壊さずに**やりたいので、
「Bubble 側でテスト用の環境を分けられますか？どう運用していますか？」と聞いてきています。

こちらがやることは、**Bubble の環境の分け方を説明して、進め方を提案する返信を書くこと**です。
今すぐ開発作業が発生するわけではありません。

---

## 2. 「ルールベース方式」とは

現在の仕組みと比べると分かりやすいです。

| | 現在（生成AI方式） | 新しい方式（ルールベース方式） |
|---|---|---|
| 作り方 | AI に「この行事のチラシを作って」と頼み、AI が画像を描く | 決まったテンプレート（下地デザイン）に、決まったルールで文字を配置する |
| たとえるなら | デザイナーに毎回おまかせで描いてもらう | 年賀状ソフトの「テンプレートに名前を流し込む」 |
| 良い点 | デザインの幅が広い | 文字崩れ・誤字がない、速い、毎回同じ品質、安い |
| 弱い点 | 文字が崩れる・遅い・結果が毎回ブレる・コストが高い | テンプレート以上の表現はできない |

「ルール」とは、たとえば
「A4 なら行事名はこの位置にこの大きさ」「はがきでは連絡先を表示しない」
といった決めごとのことです。
（宿題事項で整理した「サイズ別描画項目マトリクス」が、まさにこのルールの一種です）

つまりブラザーさんは、**AI に描かせる部分を、ルールで確実に組み立てる方式に置き換えたい**のだと考えられます。
画像を作るのはブラザーさん側（AWS）の仕事なので、**新方式の中身をこちらが作る必要はありません**。

## 3. 先方がやりたいこと

```
[いま]   ユーザー ─▶ Bubble（本番） ─▶ AWS（本番）  ※生成AI方式

[やりたい] ユーザー ─▶ Bubble（本番） ─▶ AWS（本番）  ※ここは一切触らない
           開発者   ─▶ Bubble（テスト）─▶ AWS（開発用アカウント） ※ルールベース方式を試す
```

- ブラザーさんは **AWS に開発用アカウントを新しく作り**、そこにルールベース方式の API を作る
- それを **Bubble とつないで画面から一通り動くか試したい**（＝結合テスト）
- ただし **今使っているユーザーに影響を出したくない**

そのために Bubble 側に聞いているのが次の 3 点です。

| # | 質問 | 平たく言うと |
|---|---|---|
| 1 | 本番とは別のテスト用環境を使えるか。その環境だけ接続先（URL・APIキー）を開発用 AWS に向けられるか | 「テスト用の Bubble」から「テスト用の AWS」につなげますか？ |
| 2 | dev で開発している間、main（本番）への反映はどう分離・管理しているか | 作りかけの変更が、勝手に本番に出ない仕組みになっていますか？ |
| 3 | 今後の進め方へのアドバイス | 何か注意点や良いやり方があれば教えてください |

> 「ダウンロード版アプリ」は、文脈上いま稼働中の本アプリ（原稿を生成して PPTX でダウンロードするアプリ）のことと思われます。
> 別製品を指している可能性もゼロではないので、返信で一言確認しておくと安全です。

## 4. Bubble の環境の前提知識

Bubble には「**ブランチ**」と「**環境（データベース）**」という 2 種類の分け方があります。

### ブランチ（＝画面や処理の設計図のコピー）

- 現在すでに **Main** と **dev** の 2 本がある（Bubble編集ガイドで切り替え手順を説明済み）
- dev で何を変更しても、**Main に「マージ（合流）」するまで Main には反映されない**
- それぞれに確認用の URL（version-test）がある

### 環境（＝データの入れ物）

| | 本番（Live） | テスト（version-test） |
|---|---|---|
| データベース | 本番用 | テスト用（**全ブランチで共有**） |
| 反映方法 | 「Deploy to Live」を押したときだけ | 保存すると即反映 |

ポイントは、**設計図（ブランチ）は分かれているが、テスト用のデータは全ブランチで共通**という点です。

## 5. 各質問への答え（返信の骨子）

### Q1. テスト用環境は使えるか／接続先を切り替えられるか

**使えます。** 既存の dev ブランチ（または結合テスト専用のブランチを新設）を使い、
そのブランチの API Connector の接続先 URL・APIキーを開発用 AWS のものに書き換えれば、
Main（本番）は今の AWS 本番につながったまま、dev だけ開発用 AWS につながります。

ただし確認・注意点が 2 つあります。

1. **ユーザーが今どちらの環境で使っているか**
   - ユーザーが **Live** を使っているなら、テストのデータと本番のデータは完全に別なので安全
   - ユーザーが **Main の version-test** を使っている場合、dev ブランチと**同じデータベースを共有**してしまう。
     テストで作った行事・生成結果が本番ユーザーのデータと混ざるおそれがあるため、
     テスト用アカウントを分ける等の配慮が必要
   - → **こちらで現状を確認してから返信する**（POC 中はテスト環境運用の案もあったため）
2. **APIキーの置き場所**
   - 現在キーは API Connector の設定に直接書いているため、ブランチを分ければ別のキーを入れられる
   - 「APIキー自動ローテーション」で検討中の **DB 方式に移行すると、キーはデータベースに入る**ため、
     テスト用 DB を共有するブランチ間で同じキーを見てしまう。この方式に移行する場合は、環境ごとにキーを持てる作りにする必要がある

### 【現状】ユーザーは Main の version-test で利用中

この場合、**画面や処理（ブランチ）は分けられるが、データは本番ユーザーと共有**になります。
影響が出るのは次のようなケースです。

| テストでやること | ユーザーへの影響 |
|---|---|
| テスト用アカウントで行事を作る・生成する | ユーザーからは見えない（アカウントで分かれる）。ただし**操作ログ CSV・評価ログにテストデータが混ざる** |
| デザインテンプレートや業界マスタを追加・変更する | **ユーザーの画面にもそのまま出る**（全員共通のデータのため） |
| DB に項目を追加する | 項目の追加だけなら影響は小さいが、既存項目の変更・削除は Main 側が壊れる |

ルールベース方式ではテンプレート側のデータ（ルール用の項目など）を変える可能性が高いため、**このままテストするのはリスクがある**と考えます。

**対応案**

| 案 | 内容 | 良い点 | 気になる点 |
|---|---|---|---|
| A. ユーザーを Live に移す（推奨） | Main を Deploy to Live し、データを Live にコピー。ユーザーには Live の URL を使ってもらう | 本番とテストのデータが完全に分かれる。正式リリースの手順（環境比較資料の STEP 3）もそのまま進む | ユーザーへの URL 変更の案内が必要。検索エンジン非表示・Basic 認証などの設定を Live にも適用する |
| B. 今のままテスト | dev ブランチ＋テスト専用アカウントで試す | すぐ始められる | 上表のリスクが残る。マスタ変更を伴うテストはできない |
| C. アプリごと複製する | Bubble の「アプリのコピー」で検証専用アプリを作る | データが完全に分かれる | 変更を元のアプリに戻せない（同じ改修を本体にもう一度行う必要がある）。プラン・費用の確認が要る |

→ **A を提案し、移行が終わるまでは B（マスタを触らない範囲）で進める**のが現実的です。

### Q2. dev と main の分離・管理

- 開発・検証は **dev ブランチだけ**で行う。Main は触らない
- 検証が完了したら dev を Main に**マージ**し、（Live 運用なら）**Deploy to Live** で本番に出す
- マージ前にやること
  - Main の最新状態を dev に取り込み、差分を確認
  - **接続先を本番 AWS の URL・キーに戻す（または本番 AWS 側のルールベース版に切り替える）**。
    開発用 AWS を向いたままマージすると、本番が開発用 AWS につながってしまうため
- マージ・デプロイのタイミングは、**AWS 側の本番切り替えと同じタイミングに合わせる**必要がある

### Q3. 進め方へのアドバイス（こちらからの提案）

1. **API の形が変わるかを先に決める**
   ルールベース版 API のリクエスト・レスポンス（項目、非同期かどうか、エラーの返し方）が現行と同じなら、
   Bubble 側は接続先を変えるだけで済む。変わるなら Bubble の改修が必要なので、**仕様書を早めにもらう**
2. **接続先 URL を設定値として持つ**
   URL をあちこちに直接書かず 1 か所にまとめれば、本番 / 開発の切り替えミスを防げる
3. **本番切り替えの手順と日程を事前にすり合わせる**
   AWS 本番の切り替え → Bubble のマージ・デプロイ → 動作確認、の順番と、失敗時の戻し方を決めておく
4. **テスト観点**
   全サイズ（A3 / A4 / 長尺 等）× ルール（表示する項目・しない項目）、429 などのエラー時の挙動
