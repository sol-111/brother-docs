テンプレDL版から画像生成版への切り替え設計

9月14日にテンプレートダウンロード版、10月5日に画像生成版をユーザーへ提供します。この切り替えを、当日の作業なしで自動的に成立させる方式をまとめました。動線の表示条件と、ページの入口をふさぐ条件に切替日時を仕込みます。その日時はDBの値で持ちます。

01

結論

2本の動線に表示条件を付ける。当日の作業はない

サイドメニューの動線を2本に分け、それぞれに表示条件を付けます。現在日時が切替日時を跨いだ時点で、動線は自動的に入れ替わります。10月5日に人が行う作業はありません。

動線表示する条件条件の意味
デザインテンプレ遷移先: design_tempCurrent User's Created Date < 切替日時登録が切替日時より前のユーザーにだけ表示する。切替後も既存ユーザーには残る
行事一覧遷移先: designCurrent date/time >= 切替日時切替日時を過ぎたら全ユーザーへ表示する
開発者向け: 条件を書くときに必要な情報
登録日として使う項目

User に登録日のカスタム項目はありません。組み込みの Created Date を使います。privacy rule に self（view_all: true）があるため、Current User's Created Date は本人から読めます。

条件を付ける対象

Side_main_menu の「行事一覧」（page_name = design）と「デザインテンプレ」（page_name = design_temp）の2値です。ここに日時条件を置きます。

決定: 9月14日の提供に向けて作った仕組みに条件を足すだけで、10月5日の切り替えは自動になります。
  • 2つの条件は、必ず同じ切替日時を参照してください。別々の値を書くと、片方だけ直したときに動線が1本も出ない時間帯が生まれます。
  • 動線を隠してもURLは生きています。ページの入口をふさぐ条件も別に必要です（2章）。切替日時は式に直接書かず、DBの値として持ちます（3章）。
  • この資料は書き出しファイル brother-86284.bubble を読んで作成しました。設計は9月8日 13時30分の書き出しにもとづきます。5章のレビューは9月10日 13時22分の書き出しです。
02

ページの入口をふさぐ

動線を隠しても、URLは生きている
リスク: サイドメニューの動線を隠しても、/design を直接開けば画像生成版に入れます。ブックマークや履歴からの再訪でも同じです。

design ページのリダイレクトは、もともと条件なしで常に動く作りでした。オプションセットの説明欄にある切り替え手順も「これを削除する」前提で書かれています。削除ではなく、1章と同じ条件を付ける形に置き換えます。入口は2段で守ります。

対象入れる条件入れないと起きること
design のリダイレクト「Do when condition is true」で動かすCurrent date/time < 切替日時 のときだけ動かす切替後もテンプレDL版へ飛ばされ続ける
design のメイン要素行事一覧とデザイン表示を含むグループ既定を非表示にする。Current date/time > 切替日時 のときだけ表示するリダイレクトが動かなかったときに、画像生成版の中身が見える
design_temp 側Current User's Created Date > 切替日時 なら design へ飛ばす切替後に登録したユーザーが、使えない画面に入る
  • リダイレクトを Page Load ではなく「Do when condition is true」に置くのが要点です。Page Load は一度しか走りません。切替日時がまだ読めていない瞬間に評価されると、そのまま素通りします。
  • メイン要素の既定を非表示にしておくと、切替日時が読めないときは表示されない側に倒れます。リダイレクト1つに頼らないための2段目です。
開発者向け: 入口の実装と、条件を足さない処理
入口をふさいでいる場所

design ページ（bTKwz）の ConditionTrue bTUnh0（run_when = every_time）が、Current Date/Time < Current User's switch_date's date のときに design_temp（bTTvd）へ ChangePage します。PageLoaded の版は残っていません。

メイン要素は is_visible: false が既定です。Current Date/Time > Current User's switch_date's date の条件で表示に切り替わります。

生成の監視処理に条件を足さない理由

design ページには生成の完了・失敗を見張る「Do when condition is true」が2件あります（完了 bTSdn0 / 失敗 bTSdX0）。どちらも design_generation_monitor のリスト（RG monitor・要素 bTScm0）を見ています。条件が成立すると ChangeListOfThings でモニターの deleted_at を書き換えます。

ここに切替日時の条件は要りません。RG monitor は基本のデータソースを持たず、3つとも条件付きです（is_dl_flag_ / is_regenerate_ / load_monitor_flag_）。開いた直後はどの条件も成立しないため、リストは空で count >= 1 も成立しません。フラグを立てる操作は非表示のメイン要素の中にあるので、切替前には到達できません。

design_temp 側にも同じ名前の監視処理があります（bTUid0 は filekey の取得状況を見るもの）。こちらは切替前に動く必要があるため、条件を足さないでください。

外部から直接呼べる経路

画像生成系の Backend Workflow（trigger_generated_image / generated_image / parent_re_generated_image など）は expose = false です。ページの入口をふさげば、生成を外から起動する経路は残りません。expose = true かつ認証不要は email_duplication_check と change_email の2本で、本件とは別に確認が必要です。

置き換える手順

オプションセットの説明欄にある「Roleにエンドユーザーを追加」「テンプレート版のRoleを解除」「design の page load のリダイレクトを削除」の3手順は、今回の条件付きの入口制御に置き換わります。説明欄も更新してください。

03

切替日時の持ち方

式に直接書かず、DBの値で持つ

切替日時は「2026年10月5日 9時00分」です。これを式に直接書くか、DBの値として持つかで、あとから効いてくる差が3つあります。DBの値で持ってください。

理由 1

延期にデプロイが不要になる

8月20日の議事録のとおり、画像生成はテキスト置換が期待どおりに動かず、ユーザー提供の水準に達していません。10月5日に品質が揃うかは未確定です。式に日時を直接書くと、揃っていなくても9時00分に自動で切り替わります。止めるには式を書き換えてデプロイする作業が発生します。DBの値なら日時を先送りするだけで済みます。

理由 2

切り戻しも同じ操作でできる

切り替えたあとに問題が出た場合も、日時を先送りすれば動線はテンプレDL版に戻ります。design_temp のページとデザインテンプレの動線を残しておけば、これだけで戻せます。

理由 3

参照が4か所以上に散らない

動線の条件が2本、ページの入口をふさぐ条件を加えると参照箇所は4か所以上になります。日時を各所に直接書くと、片方だけ直したときに動線が1本も出ない時間帯が生まれます。1つの値を全員が参照する形にすれば、その穴は起きません。

補足: オプションセットはアプリの定義側にあるため、値を変えて本番に効かせるにはデプロイが必要です。切替日時はオプションセットではなくDBのレコードで持ってください。

対応不要と確認

bubble_pages の突き合わせは成立している

各ページは、URLのパスセグメントと bubble_pages の表示名の一致で、自分のページ定義を引いています。引いた定義は共通部品 global の引数として渡され、未ログイン時のリダイレクトと権限による振り分けに使われます。

当初は「ページ名が design_temp に変わったのに bubble_pages の値が design_ver_tempdl のままで、定義が空になる」と指摘しました。実機で確認したところ、ログアウト状態で /design_temp を開くとログイン画面へ飛びました。この分岐は「定義の public_ が true のとき」に走るため、飛んだ時点で定義は引けています。2026年9月10日 19時06分の書き出しに入っていなかったのは、その後に直したためです。

判定のしかた: 画面が出たかどうかでは判定できません。表示は別の条件でも成立します。ログアウト状態で開いてログイン画面へ飛ぶかどうかで見てください。

あわせて分かった点があります。need_mail_confirmation は、メール未確認のユーザーを弾く条件ではありません。true のときは「メール確認済みで権限が合わないユーザーだけ、権限による振り分けを走らせる」という使われ方です。未確認のユーザーはどちらの分岐も通りません。confirm へ移るのは新規登録とメールアドレス変更の直後だけです。

対応不要と確認

切替日時が空になるケースは塞がっている

当初は「条件がすべて Current User's switch_date を経由するため、空のときに動線が消えて入口も開く」と指摘しました。実装側の3つの作りで解消済みです。実機の確認も済んでいます。

  • 紐づけ処理が全画面共通のリユーザブルの ConditionTrue にあるため、ページを開けば走る。エンドユーザーで空のまま残ることがない
  • リダイレクトが ConditionTrue（every_time）のため一度きりでない。値が入った時点で後追いで発火する
  • メイン要素が既定で非表示のため、値が読めないときは表示されない側に倒れる

毎回 Search を走らせない判断も妥当です。管理者は日付による制限を受けないため、紐づけの対象外でよいことも確認しました。

対応不要と確認

生成の監視処理に条件は要らない

当初は「生成の完了・失敗を見張る2つの処理（bTSdn0 / bTSdX0）がリダイレクトより先に評価され、生成モニターの deleted_at が書き換わる」と指摘しました。こちらも要りません。

RG monitor（要素 bTScm0）は基本のデータソースを持たず、3つとも条件付きです（is_dl_flag_ / is_regenerate_ / load_monitor_flag_）。開いた直後はどの条件も成立しないため、リストは空で count >= 1 も成立しません。フラグを立てる操作は非表示のメイン要素の中にあるので、切替前には到達できません。
